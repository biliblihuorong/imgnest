# Random image links

A random link redirects (`307`) every visit to the real direct link of a random image in one album — handy for blog backgrounds, README headers and random wallpapers.

## Shape

```
https://img.example.com/random/{uid}/{token}
```

- `uid` is the owner's 10-character random public ID and `token` a 24-character random string. Both are generated by the server, unguessable, and reveal nothing about the account.
- Enable "random image" on the album detail page. The link can be **disabled** at any time (the token survives; re-enable and it works again) or **reset** (new token; the old address stops working immediately).

## Behavior

| Case | Result |
| --- | --- |
| Default | Redirects to a random image's WebP; falls back to the original if there is no WebP |
| `?format=original` | Redirects to the original; falls back to WebP; any other value is a 400 |
| Album has no usable images, link disabled, user disabled, malformed address | The same 404 for every case — no reason is revealed |
| Too many requests | 600 per client address per minute, then 429 |

- Every usable image in the album participates, **regardless of public / private**: creating the link is the owner's explicit grant, and the UI warns that private images become anonymously reachable. Images in the recycle bin never participate.
- Responses carry `Cache-Control: no-store` and never include image metadata or EXIF.
- Resetting the token, disabling the link or disabling the user takes effect on the very next request.

## Caching and multi-instance

The candidate list is cached server-side for 60 seconds (at most 5000 images per album, randomly sampled beyond that). Album changes invalidate it proactively; without a shared cache across instances, invalidation on other instances lags at most 60 seconds — by then the redirect target is already a 404, so deleted content never leaks.
